# План редизайна СкладПромо без переписывания текущего фронтенда

Статус: уточнён по ответам владельца, без реализации  
Дата: 2026-09-08  
Авторский каталог: `docs/Codex/`

## 1. Цель документа

Спланировать редизайн витрины СкладПромо в собственной коммерческой интерпретации системы из `DESIGN-nike.md`: фотография товара и кампании несёт визуальную эмоцию, интерфейс остаётся строгим, плоским и почти монохромным, действия оформляются пилюлями, а страницы строятся на плотной сетке и ясной типографической иерархии.

Этот документ ничего не внедряет. До ответов владельца нельзя фиксировать финальные макеты, тексты, состав страниц, способ миграции и состав компонентов.

## 2. Проверенная исходная точка

### Текущий стек

- Express 4, статические HTML/CSS и vanilla JavaScript.
- Главная находится в `public/index.html`; интерактивность каталога, фильтров, корзины и заказа — в `public/js/shop.js`.
- Карточки товаров, категории, каталог и SEO-разметка частично формируются сервером в `server/seo.js`.
- Есть маршруты `/`, `/catalog`, `/category/:slug`, `/product/:slug`, `/sale`, API товаров, контактов, заказов и оптовых заявок.
- React, Tailwind CSS и `components.json` отсутствуют. Поэтому shadcn/ui нельзя просто «подключить к текущей вёрстке»: библиотека поставляет React-компоненты исходным кодом и требует отдельного React-слоя или миграции фронтенда.
- В рабочем дереве уже есть несвязанные незакоммиченные изменения. При будущей реализации их нельзя смешивать с редизайном.

### Что уже частично соответствует DESIGN-nike

- CSS-токены чёрного, белого и серого, Inter + Bebas Neue.
- Плоские карточки без теней, светло-серый фон фото, пилюли-кнопки.
- Контейнер до 1440 px, сетка каталога, липкая шапка, фильтры, корзина-панель.
- Данные о цене и наличии, SSR-метаданные, JSON-LD и индексируемые маршруты уже встроены в серверный слой.

### Что пока не даёт полноценный «photo-first commerce»

- Hero — чёрный текстовый блок без кампейн-фотографии и мобильной art direction.
- Навигация почти полностью утилитарная: нет выраженной товарной архитектуры и быстрого входа в категории.
- Главная фактически сразу переходит к каталогу; нет редакционных подборок, сценариев покупки и визуальных категорий.
- Карточкам не хватает единой модели состояний: новинка, распродажа, нет в наличии, видео, выбранный вариант, загрузка, ошибка.
- Используются emoji и неоднородные SVG вместо единой иконографики.
- Футер и блок «Как заказать» слишком краткие для коммерческого доверия; добавлять конкретные обещания без подтверждения нельзя.
- Мобильные фильтры раскрываются внутри потока, а не в полноценной доступной панели.
- Корзина и видеомодалка сделаны вручную; перед реализацией надо спроектировать управление фокусом, заголовки диалогов, клавиатурную навигацию и состояния ошибок.
- Текущие изображения товаров небольшие и неоднородные; для сильного hero и редакционных плиток нужны отдельные качественные, лицензированные материалы.

## 3. Предлагаемое дизайн-направление

Рабочая формула: **«строгий каталог склада + энергия предметной фотографии»**.

- Не копировать Nike как бренд. Заимствовать только системные принципы: контраст масштаба, плоские поверхности, сдержанный chrome, один главный CTA, плотную сетку, кинематографичную фотографию.
- Основа палитры: `ink`, `canvas`, `soft-cloud`, `muted`, `border`; красный — только подтверждённая скидка/ошибка, зелёный — подтверждённое наличие/успех.
- Один основной чёрный CTA в первом экране. Вторичные действия — мягкие или контурные.
- Hero: desktop 16:9 и mobile 4:5 с отдельными кропами, коротким доказуемым сообщением и одним действием.
- Карточка товара: фото 1:1 на `soft-cloud`, затем артикул/статус, название, цена, наличие и действие. Никаких декоративных теней.
- Типографика: Inter для интерфейса; открытый display-шрифт только для кампейн-заголовков. Финальный display-шрифт выбрать после проверки кириллицы и лицензии.
- Шаг сетки 8 px; секционные интервалы 48/32/24 px; touch target не меньше 44 px.
- Тёмную тему не включать по умолчанию: она не следует из бизнес-задачи и усложнит фото, контраст и QA. Добавлять только по отдельному решению.

## 4. Архитектурное решение: сохраняем текущий стек

### Выбранное направление — Express + vanilla UI

Сохранить Express, серверные SEO-шаблоны, публичные URL, API и существующую HTML/CSS/JS-логику. Редизайн выполнять как контролируемую переработку разметки и стилей по существующим маршрутам, без React-миграции.

`shadcn` не использовать как устанавливаемую библиотеку. Из него взять только проверенные паттерны композиции и доступности: семантические токены, единые варианты кнопок, Field/FieldGroup-подобную структуру форм, корректные группы элементов, заголовки диалогов, empty/loading/error states и управление focus.

Плюсы: не меняются стек, сборка и деплой; меньше риск для SEO и бизнес-логики; редизайн можно выпускать вертикальными срезами.  
Ограничение: компоненты будут собственными HTML/CSS/JS-композициями, а не пакетами shadcn/ui.

### Отложенная альтернатива — React/shadcn

Возвращаться к полноценному shadcn/ui только по отдельной будущей задаче, если появится продуктовая причина для миграции, а не ради одного редизайна.

### Набор навыков

- `brief-interview` — получить от владельца максимум шесть ключевых решений и затем самостоятельно собрать мега-ТЗ;
- `frontend-design` — создать самостоятельную визуальную идентичность СкладПромо поверх текущего HTML/CSS/JS;
- `prototype` — только после разрешения сделать отдельный одноразовый HTML-прототип с 2–3 вариантами одной страницы; production-файлы не менять;
- `design-jury` — после прототипа/реализации провести независимую blind-проверку desktop и mobile.

Не использовать в этом маршруте: `shadcn-ui`, `react-components`, `stitch-design`, `stitch-loop`, `design-md` и `enhance-prompt`. Они либо требуют React/Stitch, либо решают уже закрытую задачу синтеза DESIGN.md.

**Ворота A:** владелец подтверждает сохранение текущего стека и отвечает на шесть вопросов из раздела 10.

## 5. Карта собственных компонентов по паттернам shadcn

Ниже — карта HTML/CSS/JS-композиций. Названия shadcn приведены как образец поведения и доступности, а не как зависимость или команда на установку.

| Сценарий | Референсный паттерн | Собственная композиция |
|---|---|---|
| Основные и вторичные действия | `Button` | `StoreButton` с системными вариантами, без цветовых override в каждой странице |
| Поиск | `InputGroup`, `InputGroupInput`, `InputGroupAddon` | `CatalogSearch` с очисткой, loading, empty и error states |
| Фильтры | `FieldSet`, `Field`, `Checkbox`, `Accordion` | `CatalogFilters`; на mobile открывается в `Sheet` или `Drawer` |
| Быстрые наборы из 2–7 вариантов | `ToggleGroup` | чипы наличия, распродажи или компактной сортировки, если подтверждены UX-сценарием |
| Сортировка | `Select` или `DropdownMenu` | один контрол вместо набора кнопок, если тест покажет лучшую ясность |
| Карточка товара | полная композиция `Card` + `Badge` | новый flat/photo вариант на семантических токенах |
| Наличие и скидка | `Badge` + семантические токены | `StockBadge`, `SalePrice`; скидка только из подтверждённых данных |
| Пустая выдача | `Empty` | причины отсутствия и действие «сбросить фильтры» |
| Загрузка | `Skeleton` | стабильная геометрия сетки без CLS |
| Корзина | desktop `Sheet`, mobile `Drawer` | `CartPanel`, обязательный видимый или sr-only title |
| Оформление заказа | `FieldGroup`, `Field`, `Input`, `Textarea` | валидация через `data-invalid` + `aria-invalid`, состояния отправки через `Spinner` |
| Видео | `Dialog` | `ProductVideoDialog` с title, focus trap и клавиатурным закрытием |
| Характеристики | `Table` | семантическая таблица, адаптация для узкого экрана |
| FAQ и раскрытия PDP | `Accordion` | единая строка disclosure из дизайн-системы |
| Хлебные крошки | `Breadcrumb` | сохранение текущей SEO- и пользовательской иерархии |
| Уведомления | `sonner` | подтверждение корзины/заявки и ошибки с понятным следующим действием |
| Разделители | `Separator` | hairline-токены без ручных декоративных полос |

Правила будущей реализации:

- сначала переиспользовать существующие классы и поведение, затем вводить проектные варианты;
- цвета задавать семантическими CSS-переменными (`background`, `foreground`, `primary`, `muted`, `border`, `destructive`, отдельные `success` и `sale`), а не разовыми значениями в селекторах;
- формы строить структурой field group → field → label/control/description/error;
- элементы списков и меню группировать семантически;
- иконки брать из одной выбранной библиотеки, не смешивать с emoji;
- `Dialog`, `Sheet` и `Drawer` всегда имеют title;
- для overlay реализовать focus trap, Escape, возврат focus и блокировку фонового контента;
- никакие shadcn CLI-команды, registry, presets и `--overwrite` в этом варианте не используются.

## 6. Информационная архитектура и страницы

### Глобальная оболочка

- utility bar — только если есть подтверждённая полезная информация;
- primary navigation с логотипом, основными категориями, поиском, контактным действием и корзиной;
- mobile navigation в доступном drawer;
- системный footer с контактами, условиями, юридической информацией и ссылками — только на основании подтверждённых материалов.

### Главная `/`

1. Кампейн-hero с одним главным сообщением и CTA.
2. Быстрый вход в основные категории — визуальные плитки или горизонтальный rail.
3. Товарный блок «В наличии»/«Популярное» только при наличии честного правила формирования.
4. Коммерческий сценарий «Как заказать» в 3–4 шага.
5. Блок преимуществ только из доказуемых фактов.
6. Контактный CTA и доверительные материалы.
7. Индексируемый каталог/категории сохраняются в HTML и не прячутся только за клиентским JS.

### Каталог `/catalog` и категории `/category/:slug`

- единый PLP-шаблон вместо визуального расхождения между интерактивной главной и текстовыми SEO-страницами;
- desktop sidebar, mobile Sheet/Drawer;
- выбранные фильтры в чипах, явный сброс, число результатов;
- сортировка одним понятным контролом;
- 3 колонки desktop, 2 tablet, 1 или 2 mobile — финально после проверки реальных изображений и бизнес-приоритета;
- сохранение индексируемого текста и внутренних ссылок без перегрузки первого экрана;
- состояния loading, empty, API error, no image, out of stock.

### Карточка `/product/:slug`

- галерея с основным изображением, thumbnails и видео;
- название, артикул, цена, наличие/дата обновления и CTA в фиксированном порядке;
- retail и wholesale действия развести по приоритету после ответа бизнеса;
- характеристики, описание, оптовая форма, FAQ и похожие товары — в ясных секциях/accordion;
- sticky buy area на mobile рассматривать только после определения основного сценария;
- сохранить Product/Breadcrumb JSON-LD, canonical, OG и видимый фактический контент.

### Корзина и оформление

- desktop Sheet, mobile Drawer или полноэкранный шаг;
- пустое состояние, изменение количества, удаление, сумма, ошибки остатков;
- минимальная форма заказа с явными labels, подсказками, ошибками и состоянием отправки;
- сообщение об успехе не обещает сроки ответа без подтверждения.

### `/sale`

- красный применяется только к реальной скидке;
- старая цена, новая цена, процент и условия должны быть согласованы между UI, API и schema.org;
- отсутствующая/истёкшая акция не получает визуальную маркировку.

### Админка

Не включать автоматически. Если она входит в scope, спроектировать отдельно как рабочий интерфейс, не как часть editorial-витрины.

## 7. Этапы работы после согласования

### Этап 0. Ответы, факты и базовая диагностика

- получить ответы на опросник из раздела 10;
- зафиксировать основной KPI, аудитории и приоритетные маршруты;
- составить реестр доказуемых/недоказанных коммерческих утверждений;
- проверить аналитику и базовые показатели, если доступ выдан;
- снять эталонные desktop/mobile состояния текущих страниц;
- выбрать архитектуру A/B/C.

**Результат:** утверждённый brief, scope, метрики, список ассетов и архитектурное решение.

### Этап 1. Контент и информационная архитектура

- sitemap и navigation model;
- приоритет категорий и сценариев;
- content matrix: заголовок, доказательство, CTA, данные/источник, состояние;
- перечень необходимых фото и требования к кропам;
- wireflow поиска, фильтров, PDP, корзины и заказа.

**Результат:** согласованные low-fi wireframes и контентный каркас без выдуманных обещаний.

### Этап 2. Дизайн-система

- привести существующую палитру к единому набору семантических CSS-токенов;
- выбрать лицензированные шрифты с качественной кириллицей;
- определить сетку, container, typography scale, radius и states;
- описать Button, Input, Search, Badge, Card, Filters, Sheet/Drawer, Dialog, Accordion, Table, Empty, Skeleton, Toast;
- описать focus, hover, active, disabled, loading, error и success states;
- создать responsive rules и motion policy с `prefers-reduced-motion`.

**Результат:** UI inventory и токены, готовые к прототипу.

### Этап 3. Концепты и прототип

- сделать 2 концептуальных first-screen варианта в рамках одной системы: более editorial и более товарный;
- собрать high-fi для `/`, PLP, PDP и корзины;
- показать desktop и mobile одновременно;
- проверить прототип на 5 основных задачах: найти товар, отфильтровать, понять цену/остаток, запросить опт, оформить заказ;
- выбрать один вариант и зафиксировать причины.

**Результат:** утверждённый визуальный и UX-прототип.

### Этап 4. Технический каркас без миграции

- создать отдельную ветку/изолированную рабочую область;
- сохранить Express и vanilla HTML/CSS/JS;
- создать семантические токены в существующем глобальном CSS-файле;
- выделять повторяемые шаблоны постепенно, без новой UI-зависимости;
- переносить текущие обработчики по одному и проверять функциональный паритет;
- ввести слой данных, не дублирующий существующие правила цены/остатка/скидки.

**Результат:** компонентный стенд без переключения публичных маршрутов.

### Этап 5. Реализация страниц по вертикальным срезам

Порядок: оболочка и навигация → каталог/категории → PDP → корзина/заказ → главная editorial → sale → при отдельном scope админка.

Каждый срез включает desktop/mobile, состояния, accessibility, SSR/SEO и тесты функционального паритета.

### Этап 6. Проверка

- функциональный паритет поиска, фильтров, сортировки, корзины, заказов, оптовых заявок, видео и контактов;
- keyboard-only, focus order/trap/return, accessible names, live regions, ошибки форм;
- контраст, zoom 200%, ширины 320/375/768/1024/1440/1920;
- изображения: aspect ratio, lazy loading, art direction, alt, no-image;
- SEO: 200/301/404, canonical, metadata, JSON-LD, sitemap, robots, внутренние ссылки и SSR HTML;
- производительность: целевые LCP ≤ 2,5 c, INP ≤ 200 мс, CLS ≤ 0,1 на ключевых шаблонах при реальном измерении;
- визуальная регрессия ключевых страниц и состояний;
- проверка аналитических событий до/после, если аналитика доступна.

### Этап 7. Выпуск

- preview/staging;
- при возможности feature flag или поэтапное переключение маршрутов;
- отдельное подтверждение владельца перед деплоем;
- post-release smoke для заказа и оптовой заявки без создания ложных production-заказов;
- мониторинг ошибок, конверсии и Core Web Vitals;
- rollback-план, связанный с конкретным релизом.

## 8. Критерии приёмки редизайна

- Визуальная система узнаваема как СкладПромо, а не имитация Nike.
- Один главный CTA на первом экране; иерархия действий остаётся ясной на всех ширинах.
- Все ключевые сценарии работают не хуже исходного сайта.
- Публичные URL и SEO-сигналы сохранены или мигрированы с доказанным паритетом.
- Текст и UI не содержат неподтверждённых цен, сроков, условий, наличия, доставки, нанесения или юридических утверждений.
- Все собственные компоненты следуют согласованным паттернам композиции, семантическим токенам и доступности; нет локального хаоса цветов и вариантов.
- Все интерактивные элементы доступны с клавиатуры, имеют видимый focus и корректные accessible names.
- Нет горизонтального скролла на 320 px; touch targets ≥ 44 px.
- Loading/empty/error/success/out-of-stock/no-image состояния спроектированы, а не добавлены постфактум.
- Показатели производительности измерены на staging/production, а не заявлены по сборке.

## 9. Риски и ограничения

- Без кампейн-фотографии photo-first концепция превратится в типографический рестайлинг.
- Внедрение React/Vite/Next ради редизайна исключено из текущего scope; возвращаться к нему только отдельным архитектурным решением.
- Проприетарные Nike Futura и Helvetica Now нельзя считать доступными; нужен лицензированный или открытый кириллический эквивалент.
- Жёсткое копирование Nike создаст слабую самостоятельность бренда и возможные правовые/репутационные риски.
- Текущие данные и коммерческие тексты не подтверждают автоматически доставку, минимальный заказ, сроки ответа, нанесение логотипа, упаковку, возврат, географию и юридические реквизиты.
- Редизайн одновременно с архитектурной миграцией увеличивает объём; нужен этапный rollout.
- Существующие незакоммиченные изменения требуют изоляции, инвентаризации и аккуратного объединения.

## 10. Шесть вопросов владельцу

Навык `brief-interview` ограничивает бриф шестью решениями: пользователь выбирает направление, а детализацию, структуру и список допущений готовит дизайнер. Если нужного варианта нет, можно дать свой.

Ответы получены 2026-09-08: спокойная практичность; B2B-закупщики/маркетологи; оформление заказа; самостоятельная editorial-интерпретация DESIGN-nike; только товарные фотографии; первая очередь без sale и админки. Итоговое мега-ТЗ сохранено в `docs/Codex/REDESIGN_BRIEF_SKLADPROMO_2026-09-08.md`.

1. **Ощущение первых трёх секунд:** доверие и профессионализм / энергия и желание действовать / статус и премиальность / спокойная практичность / своё.
2. **Главная аудитория:** B2B-закупщик или маркетолог / агентство-посредник / малый бизнес и ИП / частный покупатель / гибрид с указанным приоритетом.
3. **Главное действие:** оформить заказ / запросить оптовые условия / написать менеджеру / найти товар и посмотреть наличие / своё.
4. **Визуальная дистанция от DESIGN-nike:** только системные принципы / заметная editorial-эстетика, но свой бренд / максимально близко по композиции; рекомендация — второй вариант.
5. **Ассеты:** есть логотип, бренд-цвета и качественные hero/категорийные фото / есть только логотип / есть только товарные фото / можно организовать съёмку или согласовать генерацию фонов.
6. **Scope первой версии:** главная + каталог/категории + PDP + корзина / добавить sale и коммерческие страницы / включить также админку; рекомендация — первый вариант, админку отдельно.

Из ответов дизайнер самостоятельно соберёт мега-ТЗ: аудитории и возражения, эмоциональную дугу, CTA, структуру страниц, визуальную систему, shot list, перечень непроверенных коммерческих фактов и критерии приёмки. Неизвестное маркируется как `НЕТ ДАННЫХ` или `[допущение]`.
